## Introduction
LSM-Tree 是现代高性能键值存储系统的核心架构之一，被广泛应用于 RocksDB、LevelDB 及其衍生系统中。相较于依赖原地更新的 B+ 树，LSM-Tree 通过将随机写转化为顺序追加写，显著降低了写路径上的随机 I/O 开销，因此在写密集型工作负载下通常能够提供更高的写入吞吐。然而，这种写优化架构也引入了多版本共存、跨层文件重叠以及读放大、写放大和空间放大等经典问题。为维持查询效率与存储有序性，现有系统通常依赖 Bloom Filter、索引块以及后台 Compaction 对 SST 文件进行持续归并与重写。在带宽受限的存储环境中，系统瓶颈往往不再来自前台写入本身，而是来自后台维护过程长期占用的大量 I/O 带宽。
这一问题在大 Value 场景下尤为突出。传统 LSM-Tree 将 Key 与 Value 作为整体在各层之间反复下推，使得大对象在多轮 Compaction 中被重复读取与重写，进而显著放大后台 I/O 成本。为缓解这一问题，TerarkDB 在 RocksDB 基础上引入了键值分离架构：将较小的 Key 及其元数据保留在主 LSM-Tree 中，而将实际 Value 剥离并顺序追加写入独立的 Blob 文件，主树仅维护指向 Blob 数据的引用。该设计有效避免了大对象随层级 Compaction 被反复搬运，因此显著降低了大 Value 负载下的写放大和后台重写开销。
然而，键值分离并没有消除后台维护代价，而是将问题从 Compaction 转移到了 Blob 垃圾回收（GC）阶段。随着更新和删除不断发生，Blob 文件中会逐渐积累大量失效对象；一旦某个 Blob 的垃圾比例超过阈值，系统便必须启动回收流程。现有 Blob GC 通常需要扫描候选 Blob 中的对象，并逐条回查主 LSM-Tree，以验证对象是否仍然有效以及引用是否仍指向当前 Blob 文件。这样的“盲读-反查”流程会引入大量额外的随机点查、对象验证以及无效数据读取，不仅持续消耗后台 I/O 与 CPU 资源，也会与前台请求竞争有限的设备带宽，从而导致吞吐下降和尾延迟恶化。换言之，键值分离降低了大 Value 在 Compaction 中的重写代价，却并没有从根本上解决后台带宽争用问题。
已有工作主要沿着两条思路降低键值分离系统中的 GC 成本。第一类方法通过冷热分层或生命周期感知布局，将不同寿命的数据放置到更匹配的存储单元中，以减少后续迁移代价。第二类方法则通过 drop-key list、辅助索引甚至额外的 LSM-Tree，在 GC 期间重建对象有效性视图，从而减少对主树的直接反查。这些方法各自取得了一定效果，但大多只优化了问题链条中的局部环节。前者回答了对象“应该写到哪里”，却没有回答如何让失效对象在 Blob 粒度上更快收敛，从而形成真正高回报的回收目标；后者试图降低 GC 阶段的验证成本，却仍然需要在回收时额外重建有效性信息，或维护额外索引结构。更关键的是，现有方案通常将垃圾形成、失效信息维护和回收执行割裂开来，因而仍难以在带宽受限环境中同时降低垃圾生成成本、有效性识别成本和回收执行成本。
本文的核心观察是：在键值分离 LSM 中，Blob GC 的带宽低效并不单纯由垃圾比例决定，而是源于三个关键因素之间的脱节。首先，失效对象能否在 Blob 内部快速且集中地收敛，决定了系统能否形成值得回收的高价值 Blob；其次，对象有效性是否能够随着版本演化被在线物化，而不是等到 GC 启动后再临时重建，决定了回收过程是否仍需承担高昂的验证开销；最后，活数据在 Blob 内部的空间分布是否能够被准确揭示，决定了系统能否选择带宽代价最低的回收路径。现有系统的根本问题正在于这三者彼此脱节：垃圾被被动地产生，失效信息在 GC 时才被重建，而回收则通常采用统一的扫描-验证-重写流程。
基于这一观察，本文提出一种面向键值分离 LSM 的带宽高效 Blob GC 闭环设计，并在 TerarkDB 中实现了原型系统。我们的设计围绕 Blob GC 构建了一条从“垃圾形成”到“垃圾表达”再到“垃圾回收”的协同路径。首先，为了提升失效对象在 Blob 粒度上的收敛性，我们提出一种面向 GC 的写路径塑形机制，利用轻量级 Window + Hot Table 在线捕获对象的短期覆盖风险，并通过非对称准入策略将更新请求分流到不同类型的 Blob 中。与传统生命周期感知方法不同，该机制并不追求精确预测对象的长期寿命，而是直接以提升 Blob 级死亡率、抑制冷 Blob 污染为目标，从源头上主动塑造更易回收的数据布局。
其次，为了消除 GC 阶段高成本的有效性重建，我们提出一种与 Compaction 耦合的确定性失效跟踪机制。不同于现有方法需要在 GC 启动后通过主树反查或额外索引重建对象有效性，我们利用 LSM-Tree 在 Compaction 过程中已经由版本语义确定的失效事件，在线维护 Blob 级失效位图。因而，GC 启动时获得的是一份现成可用的有效性视图，而非需要临时构建的判断结果。基于该位图，GC 不再需要执行传统的“盲读-反查”流程，而是可以直接定位并读取仍然存活的数据，将回收从“查证式”过程转化为“消费式”过程。这不仅避免了对主 LSM-Tree 的高成本干扰，也为后续按需读取有效数据提供了精确依据。
最后，为了进一步降低回收执行本身的带宽成本，我们提出一种位图驱动的多模式 Blob 回收机制。我们观察到，仅知道 Blob 的整体垃圾比例仍不足以决定最优回收路径，Blob 内部活数据是连续分布、稀疏分布还是局部聚集，同样直接影响回收代价。因此，我们联合利用前述写路径塑形形成的 Blob 类别以及在线失效位图揭示的活数据空间分布，在整文件退休、块级稀疏回收和延迟回收等多种执行模式之间进行自适应切换。与统一的重写式 GC 相比，该设计能够将不同 Blob 映射到带宽代价最低的回收路径，从而进一步减少无效数据读取和不必要的数据搬迁，并缓解后台 GC 对前台请求的带宽干扰。
我们在 TerarkDB 原型上实现了上述设计，并在多种写密集和更新密集工作负载下进行了评估。实验结果表明，本文方法能够显著降低 Blob GC 的后台读写带宽占用，减少对主 LSM-Tree 的查询干扰，并有效改善前台吞吐与尾延迟表现。具体而言，相较于现有 TerarkDB 键值分离实现，我们的方法将 GC 读带宽降低了 [X%–Y%]，将前台写入吞吐提升了 [A%–B%]，并将前台 p99 时延降低了 [M%–N%]。这些结果表明，在带宽受限环境下，围绕垃圾形成、失效信息物化和回收执行构建协同闭环，是进一步释放键值分离 LSM 性能潜力的关键。
综上，本文做出了如下贡献：
- 提出一种面向 GC 的写路径塑形机制，利用轻量级 Window + Hot Table 在线估计对象的短期覆盖风险，并通过非对称准入策略主动构造高死亡率 Blob、降低冷 Blob 污染。
- 提出一种与 Compaction 耦合的确定性失效物化机制，将 LSM-Tree 版本演化过程中已确定的失效事件在线转化为 Blob 级失效位图，使 GC 不再依赖传统“盲读-反查”流程重建对象有效性。
- 提出一种位图驱动的多模式 Blob 回收机制，联合利用 Blob 类别与失效位图揭示的空间分布，在整文件退休、块级稀疏回收和延迟回收之间自适应切换，以最小化后台带宽消耗。
- 在 TerarkDB 上实现原型并进行了系统评估，结果表明本文设计能够显著降低 Blob GC 开销，并提升带宽受限场景下的整体系统性能与前台服务质量。

## Motivation and Challenges

尽管键值分离显著降低了大 Value 在 LSM-Tree Compaction 中的重复搬运成本，但我们在 TerarkDB 上的观察表明，系统瓶颈并未随之消失，而是以另一种形式重新出现在 Blob GC 路径上。尤其在带宽受限设备和更新密集负载下，后台 GC 往往不再是一个低频、可忽略的维护过程，而是持续占用设备带宽、放大前后台资源竞争的主要来源。因此，在进入具体设计之前，有必要进一步回答两个问题：第一，现有键值分离 GC 究竟为何在实际系统中仍然昂贵；第二，如果目标是系统性降低后台带宽消耗，那么真正困难的挑战是什么。

### Motivation

首先，现有 Blob GC 的高开销并不主要来自“复制了多少活数据”，而是来自在回收前必须完成的大量有效性验证工作。在传统实现中，GC 只能从候选 Blob 出发，逐个读取对象元数据，再逐条回查主 LSM-Tree，以判断该对象是否仍然存活以及主树中的引用是否仍然指向当前 Blob。这个过程本质上是一种事后求证机制：系统在对象失效时并不立即记录其死亡事实，而是把判断工作推迟到 GC 启动时再集中完成。结果是，GC 即使面对一个垃圾占比很高的 Blob，也仍需先付出大量随机查证代价，才能真正开始回收。这种“盲读-反查”式流程将回收成本与对象数目而非活数据规模绑定，从而在更新密集场景下表现出很差的带宽效率。

其次，现有系统中的垃圾往往难以在 Blob 粒度上快速收敛，导致系统难以形成真正“值得回收”的高价值对象。理想情况下，GC 最希望面对的是一类短时间内迅速死亡、内部失效对象高度集中的 Blob，因为这类 Blob 可以用较小代价换取较大回收收益。然而，传统写入路径通常只关注写入吞吐与空间利用率，并不会主动区分对象的短期覆盖风险。结果是，不同更新行为和不同寿命的数据被混合写入同一批 Blob 中，形成严重的冷热污染：热点对象反复失效，冷对象长期存活，两者交织在一起，使得许多 Blob 长期处于“垃圾不低但也不够高、可回收但回收收益有限”的尴尬状态。此时即使触发 GC，系统也不得不为少量活数据和大量分散垃圾支付高昂扫描与迁移成本。

甚至即便系统已经知道某个 Blob 的整体垃圾比例，仍然无法据此直接推导最优的回收方式。两个垃圾比例相同的 Blob，其内部活数据分布可能完全不同：有的 Blob 只在少量局部区间保留活数据，适合块级或区间级选择性读取；有的 Blob 活数据近乎连续，更适合整体搬迁；还有的 Blob 虽然存在垃圾，但当前阶段回收收益仍不足以覆盖额外 I/O 成本，更适合延后处理。换言之，垃圾比例只是一个粗粒度信号，它并不能揭示 Blob 内部活数据的空间结构，而后者恰恰决定了回收执行路径的带宽代价。现有 GC 往往采用统一的扫描-验证-重写流程，缺乏对这种空间异质性的利用，因此会产生大量原本可以避免的无效 I/O。

最后，Blob GC 的问题之所以在带宽受限环境中尤为突出，是因为它不仅消耗后台资源，还会直接干扰前台服务质量。无论是扫描候选 Blob、回查主 LSM-Tree，还是迁移活数据并重建索引，都会与前台读写共享同一套设备带宽、I/O 队列和缓存资源。当后台 GC 以“高读放大 + 高验证开销 + 高搬迁代价”的方式运行时，前台请求即便逻辑路径很短，也可能因设备拥塞和队列排队而遭受明显的吞吐下降和尾延迟抖动。因此，对于键值分离系统而言，真正需要优化的不仅是 GC 的功能正确性，而是其在全系统带宽预算中的效率和友好性。

### Challenges

基于上述观察，构建一个真正带宽高效的 Blob GC 系统至少面临以下几个核心挑战。

第一，如何在不显著增加前台写路径开销的前提下，主动塑造更易回收的数据布局。要让垃圾在 Blob 粒度上快速收敛，系统必须在写入时感知对象的短期覆盖风险，并尽可能将高风险对象与稳定对象分离存放。然而，对象寿命本身具有强动态性和工作负载相关性，系统很难在写入瞬间准确预测其长期行为。如果为此引入复杂的在线学习、重型统计结构或精细分类机制，又会显著增加前台写入延迟与实现复杂度。因此，第一个挑战在于：如何仅利用轻量级、在线可维护的信号，在写路径上以很低代价获得足够有效的垃圾收敛效果。

第二，如何将对象失效信息从“GC 时临时重建”转化为“版本演化中在线物化”，同时保证语义正确性。表面上看，若能在对象失效时立即记录其死亡状态，GC 便可省去大量主树反查开销；但在实际 LSM 系统中，对象是否真正失效受到多版本可见性、Compaction 过程、快照语义以及引用重定向等因素共同影响。系统不能仅凭一次覆盖写入就贸然断言旧对象已可回收，否则容易破坏版本正确性或恢复一致性。因此，第二个挑战在于：如何找到一个既足够“晚”以保证语义确定、又足够“早”以避免 GC 时重新查证的时机，将失效事件可靠地在线转化为可消费的元数据表示。

第三，如何以低额外开销维护足以驱动高效回收的细粒度有效性视图。即便系统能够在线感知对象失效，也并不意味着可以无代价地维护 Blob 级活性状态。过于粗粒度的统计信息只能支持简单阈值触发，无法支撑块级稀疏回收等精细执行路径；而过于细粒度的索引结构虽然表达能力更强，却可能带来较高的内存消耗、写放大和恢复负担。因此，第三个挑战在于：如何设计一种既紧凑又足够精确的失效表示，使其既能避免 GC 阶段的高成本验证，又能揭示 Blob 内部活数据的空间分布，为后续回收模式选择提供依据。

第四，如何根据 Blob 的活数据空间分布自适应选择回收模式，而不是采用单一路径处理所有对象。统一的重写式 GC 实现简单，但会忽略 Blob 之间显著不同的结构特征，导致大量不必要的数据读取与迁移。相反，若系统希望在整文件退休、块级稀疏回收和延迟回收等模式之间切换，就必须回答何时切换、依据什么切换，以及切换是否稳定等问题。错误的模式选择不仅无法节省带宽，反而可能引入更多元数据维护与调度成本。因此，第四个挑战在于：如何把失效比例、空间分布和未来收益统一纳入回收决策，使不同 Blob 都能映射到其带宽代价最低的处理路径。

综合而言，键值分离系统中的 Blob GC 问题并不是单一算法优化问题，而是一个横跨写入、版本演化和后台回收的协同设计问题。仅优化其中任意一个环节，都难以从根本上降低后台带宽消耗并缓解前后台竞争。基于此，后续章节将围绕“垃圾形成、失效信息物化与多模式回收执行”三个环节展开，介绍我们如何在 TerarkDB 中构建一个面向带宽效率的 Blob GC 闭环设计。

## Design Overview and Detailed Design

## Implementation

我们在 TerarkDB 上实现了原型系统，整体遵循设计章节中的三条主线，并尽量复用现有 KV separation、Compaction 和 Blob GC 框架，而非引入一套独立的后台子系统。实现工作的目标不是重构 TerarkDB 的存储引擎主流程，而是在保持原有写入、版本演化和回收框架基本不变的前提下，把“垃圾形成、失效物化与回收执行”三个环节真正串联起来。

首先，在写路径塑形部分，我们将轻量级 Window 与 Hot Table 集成到现有写入与分离流程中，用于在线捕获对象的短期覆盖风险，并据此执行非对称准入。实现上，该模块位于 memtable 写入之后、value separation 之前，仅维护常数级热点状态，不改变前台请求的基本处理语义，也不引入额外的后台线程。系统不追求精确预测对象的长期寿命，而是仅判断对象是否更可能在短时间内被覆盖，并据此将其写入不同类别的 Blob，以提升失效对象在 Blob 粒度上的收敛性，减少冷热数据混写带来的 GC 污染。

其次，在失效信息物化部分，我们将失效记录的维护与 Compaction 过程耦合。TerarkDB 原有的 Compaction 已经能够基于版本语义判断旧引用何时被新版本替代，因此我们不再等到 GC 启动后通过“扫描 Blob + 回查 LSM”重建对象有效性，而是在 Compaction 产出新 SST 时同步记录其对 Blob 文件的依赖关系和失效贡献。具体而言，我们在 SST 的表属性以及 VersionEdit/Manifest 中扩展了 Blob dependence 元数据，使每个新生成的 SST 文件能够携带其依赖的 Blob 文件编号及相应统计信息；VersionBuilder 在安装新版本时再基于这些依赖关系累计每个 Blob 的失效程度，并将结果写回内存中的文件元数据。这样，GC 在选择候选 Blob 时即可直接利用版本演化过程中已经在线物化的失效信息，而无需再次对主树执行大规模反查。该实现仍复用原有 Manifest 日志与版本恢复流程，因此不会引入额外的恢复子系统。

在上述实现过程中，我们进一步加入了一个配套的工程优化，即 `precise_gc`。TerarkDB 原有 Blob GC 主要依据失效 entry 数量估计垃圾比例，这种口径在 value 大小近似均匀时较为简单有效，但在 value size 波动明显的负载下，条目数比例与真实无效字节占比之间可能出现系统性偏差，从而使系统过早或过晚触发某些 Blob 的回收。为此，我们在依赖元数据中增加了可选的字节统计信息，并在 Blob GC 选择候选文件时支持按照失效字节占比计算垃圾率。实现上，该优化并未改变 GC 主流程，而是在 Flush 或 Compaction 生成新 Blob 或新依赖关系时顺带记录更精确的 byte-based 统计；若某些路径下无法获得精确字节信息，则系统自动回退到原有的 entry-based 估算方式。因此，`precise_gc` 本质上是对现有 GC 统计口径的实现级增强，而非独立的新 GC 机制。它的作用是减少负载不固定、value 大小分布不均场景下的统计误差，使候选 Blob 的选择更贴近真实带宽回收收益。

最后，在回收执行部分，我们复用现有 Blob GC 调度与文件管理框架，并在其上扩展位图驱动的多模式执行逻辑。GC 不再统一采用扫描-验证-重写流程，而是根据 Blob 的失效比例以及活数据的空间分布，在整文件退休、块级稀疏回收和延迟回收等模式之间切换。实现上，这一部分并未改变 TerarkDB 的基本文件组织方式，而是将前述在线物化得到的失效视图转化为回收阶段的调度依据。这样，写路径塑形负责改善垃圾形成质量，失效物化与 `precise_gc` 提供可直接消费的垃圾表达，而多模式执行则进一步将这些信息转化为实际的带宽节省。

从工程实现角度看，上述改动均遵循“复用现有组件、增量扩展元数据、避免引入重型后台结构”的原则。新增信息主要通过表属性、VersionEdit 和内存中的文件元数据在现有生命周期内传播；旧格式在缺失新增字段时仍可退化为原有估算逻辑，因此具有较好的兼容性与恢复友好性。
